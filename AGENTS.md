# AGENTS.md

PickMyClass emails ASU students when a watched class section gains an open seat or gets a named instructor. It is a Next.js 16 App Router app (React 19, strict TS) built by **vinext** (Vite-based) and deployed as one **Cloudflare Worker**, with PlanetScale Postgres through Hyperdrive (request-scoped Drizzle over node-postgres (`pg`)), Clerk auth, Cloudflare Workflows + Queues for scheduled seat checks, and Cloudflare Email for delivery. Features, architecture diagram, and self-hosting are in [README.md](README.md). Use these domain terms in code, tests and issues: `SectionRef` (the `{ class_nbr, term }` pair that identifies a section), Section Check (one `processSection` run for one `SectionRef`) and Cron Cycle (one `SectionCheckWorkflow` run, every 15 minutes; its `cycle` stamp rides on each queue message).

When code and this file disagree, code wins: fix this file in the same change.

## Repo map (non-obvious parts only)

- `worker.ts`: the Worker entry. Wraps vinext `fetch`, adds `queue()`, re-exports the Workflow classes. Queue messages call `processSection()` directly, with no HTTP hop.
- `proxy.ts`: vinext middleware. This is **the** auth gate and the CSP builder (decision logic in `lib/auth/decide-gate.ts`).
- `lib/workflows/cron-workflows.ts`: `SectionCheckWorkflow` (every 15 min, even/odd stagger, so each section is checked every 30 min) and `MaintenanceWorkflow` (04:05 UTC).
- `lib/queue/`: the seat-check pipeline (`process-section.ts` orchestrates, `change-detector.ts`, `notification-sender.ts`, `section-retirement.ts`). `pending-notifications.ts` owns durable notification intent and delivery leases; `notification-claims.ts` resumes intent-owned, unconfirmed claims after crashes.
- `lib/db/index.ts`: the only DB seam (`getDb(hyperdrive)` / `getDbFromEnv()`, request-scoped). `lib/db/queries.ts` holds the Drizzle builders and typed SQL calls to `SECURITY DEFINER` RPCs. `lib/db/schema/` defines the tables.
- `migrations_pg/`: drizzle-kit migrations, the real schema history, tracked in `drizzle.__drizzle_migrations`. `lib/db/schema/` is the source of truth for tables: edit it, then `db:generate`. Functions, triggers and data fixes go in `pnpm run db:generate --custom` files; change a function with `CREATE OR REPLACE` in a new migration, never edit an applied file. `0000_baseline` + `0001_baseline_functions` reproduce prod as of 2026-10-01. `db/migrations/` is frozen pre-drizzle history; never add to it.
- `lib/utils.ts` is shadcn's `cn()` only. Custom helpers go in `lib/utils/`. The split is intentional, so leave both.
- `lib/seo/`: sitemap, `/llms.txt` and `/llms-full.txt` route handlers, lastmod map, IndexNow.
- `tests/integration`: all tests live here, not next to source. The `test` block in `vite.config.ts` defines `integration` and opt-in `db` projects. `tests/mocks/` stubs `cloudflare:workers` and the vinext entry through `test.alias`. `tests/mocks/scripted-postgres.ts` is a scripted node-postgres transport for API integration tests.
- `tools/oxlint/anti-slop/`: vendored lint plugin (see Gotchas).

## Conventions (enforced by lint or used everywhere)

- **API routes:** wrap handlers in `withAuth(request, async (user) => …)` from `lib/api/withAuth.ts` (401 on `UnauthorizedError`). Validate with `parseOrFail(schema, body)` from `lib/api/validation.ts` (schemas in `lib/api/schemas.ts`). Respond with `ok()` / `fail(msg, status)` from `lib/api/response.ts`. `app/api/class-watches/route.ts` shows the full pattern. `monitoring/health` authenticates with `verifyCronSecret`.
- **Bindings:** `import { env } from 'cloudflare:workers'`. DB access goes through `getDbFromEnv()`, not a module-level client.
- **Logging:** `log('Scope').info|warn|error(msg, fields)` from `lib/log.ts` writes one `{ level, scope, msg, ...fields }` object per line, so every key is queryable in HyperDX. Keep `msg` constant and put ids, counts and `duration_ms` in fields (`sectionFields(ref)` for a SectionRef), never interpolated. A caught value goes in as `...errorFields(error)` (message, name, SQLSTATE, stack; strips Drizzle bound params, redacts emails), never `String(error)`. Product events (watch created/deleted, signup, unsubscribe, account deletion) use `logEvent(name, fields)` from the same file: one object per event so Workers Logs indexes the fields for HyperDX. Add new events to its `ProductEventMap`; fields are opaque ids only, never emails or names. `no-console` is a lint error outside `lib/log.ts`, `scripts/`, and `tests/`.
- **Type assertions** need a `// SAFETY: …` comment directly above them (`anti-slop/require-safety-comment-for-type-assertion`). Chained `as unknown as X` is banned outright. Other anti-slop rules to know: no object-shaped parameters, no `unknown` params or returns, no `.filter().map()`, no spread-accumulating `reduce`. The full list is in `vite.config.ts` → `lint.rules`.
- **Imports:** `@/…` path alias. `vite-plus/test` instead of `vitest` (the `vite-plus/prefer-vite-plus-imports` rule enforces it).
- **Effect:** Effect v4 wraps the server's external calls at the leaf, never the code between them. `externalCall` (`lib/effect/external-call.ts`) is the one shape: a Promise attempt with an `AbortSignal`, an explicit timeout, and two tagged errors the integration owns (`*Failed` with a `retryable` flag, `*TimedOut`). The ASU client (`lib/asu/asu-client.ts`) adds runtime schemas; `fetchClassFromASU` (`lib/asu/api.ts`) owns the cache and maps tags to the legacy `ApiError` classes. The database is guarded in `lib/db/guard.ts`: `getDb` wraps every `pool.query`/`pool.connect` client query in `DB_QUERY_TIMEOUT_MS` and throws `DbQueryFailed`/`DbQueryTimedOut` (both extend `Error`, so existing `catch` blocks and `getPgError` still work). A timeout is an unknown outcome, not "didn't happen": a client-side timeout does not cancel the server statement, and a timed-out email send (`EmailTimedOut`, from `lib/email/transport.ts`, the only caller of the `send_email` binding) stays in-flight rather than rolling back. Retries are decided by the layer that owns them (the queue consumer and Workflow steps, via `retryable`); never add `Effect.retry` beneath them. Queue producers go through `sendQueueBatch` (`lib/queue/transport.ts`); the consumer validates each body with `classCheckMessageSchema` (a malformed one is retried so it lands in the DLQ with its payload) and acks a thrown failure with `retryable: false`; Workflow step bodies that can throw a typed failure wrap in `failPermanently` (`lib/workflows/step-errors.ts`), which turns a permanent failure into Cloudflare's `NonRetryableError` and leaves the rest to the step's `retries`. Keep orchestration (Section Check, notification, delivery) plain async/await: nothing interrupts it, and a Worker eviction skips finalizers anyway. Delivery releases unattempted/failed claim IDs and the intent lease in `finally`, and keeps delivered and in-flight claims. Clerk calls go through `clerkCall` in `lib/auth/clerk-session.ts` (timeout, `ClerkCallFailed`/`ClerkCallTimedOut`, retry decision from the HTTP status); the Clerk client is built per call, never cached at module scope, and a sign-out-everywhere that leaves sessions active throws `SessionRevocationIncomplete`. The Clerk webhook parses `event.data` with `clerkWebhookUserSchema` and answers 422 on a signed payload of the wrong shape. Effect never enters code the browser loads (`tests/integration/effect/browser-boundary.test.ts` pins it). The `anti-slop-effect` lint rules (Match over `_tag` switches and literal ternaries, tagged constructors over literal `_tag` objects) apply to `lib/asu/**`, `lib/effect/**`, `lib/db/**` and their tests; add a path to that override in `vite.config.ts` when Effect reaches a new area. Effect tests use `it.effect` from `@effect/vitest` with assertions/mocks from `vite-plus/test`; virtual time comes from `effect/testing`.
- **Constants** go in `lib/config.ts`. Style: Oxfmt defaults (2 spaces, width 100, double quotes, semicolons, trailing commas everywhere); `pnpm run fix` applies it.
- **Email:** every template value passes through `escapeHtml` (`lib/utils/escape-html.ts`). Unsubscribe tokens are stateless HMAC, valid 90 days, reusable.
- **Tests** stub external services and use `createScriptedPostgres` for API database queries rather than hitting real services. Name files `*.test.ts(x)` under `tests/integration/`; the live database project is opt-in.
- **Commits:** Conventional Commits, `type(scope): summary`.

## Gotchas and invariants

**Seat-check pipeline**:
- `processSection` resumes pending notification intent before its cycle guard. `readSectionCheckState` returns `has_pending_intent` (live or expired), and only a flagged section runs `deliverPendingNotifications` before the check (whose acquire step also clears expired intents), then re-reads the state; after the check it delivers only when `record_section_observation` reports `intent_created`. A check with no pending intent is therefore two queries. `record_section_observation` accepts the observation, resets claims and saves notification intent in one transaction under the existing SectionRef advisory lock. It computes transitions from the locked stored row, suppresses first-observation alerts and rejects stale observations. A pending intent must finish or expire before another observation replaces it.
- Delivery leases are per intent, never a cron lock. Claims carry `delivery_intent_id`; `delivered_at` distinguishes confirmed delivery from an interrupted claim. Resume unconfirmed claims for the same intent and retain successful claims. Complete/release using both intent ID and lease ID. Intent expires after 30 minutes to resume fresh observations after a provider outage; discard only its unconfirmed claims once no live lease exists. A provider accepting an email just before the Worker dies can still produce a duplicate on retry: delivery and the database cannot commit atomically.
- Email only the watch IDs returned by `tryRecordNotificationsBatch` or its intent-aware `claim_section_notifications` wrapper. Roll back failed sends with the row IDs from that same claim (`deleteNotificationRecordsByIds`), never by re-looking-up the active row, which can delete a newer claim.
- The first-observation guard (`!oldState` → no seat email) prevents false alerts. Keep it.
- There is deliberately no cron lock. Overlapping Workflow instances are made safe by the message `cycle` stamp plus the conditional upsert. Keep both guards and don't add a lock.
- `processSection` owns ack/retry (`SectionCheckOutcome`); callers only translate it for the transport. ASU 429s back off via `retryDelaySeconds()` (60s doubling, honours `Retry-After`, 15-min cap). Invalid responses are terminal and acked; only transport failures retry. Seat counts must be usable; unknown counts are acked rather than zero-filled. Busy notification intent retries wait for the 16-minute lease rather than exhausting the delivery attempts before the owner can be replaced; its lease is shorter than the 30-minute intent lifetime.
- `expire_stale_notifications()` runs in every `SectionCheckWorkflow` run and in `MaintenanceWorkflow`. Re-notifications stop without it.
- `class_states` is keyed on `(class_nbr, term)`. Always carry both (`SectionRef`).
- `lib/asu/terms.ts` generates ASU terms from weekday rules (e.g. fall starts the Thursday on or after Aug 17), so the calendar never runs out. `TERM_DATE_OVERRIDES` holds known dates the rules miss. When ASU publishes a calendar that differs, add an override; `tests/integration/asu/terms.test.ts` pins every known date.
- Seat signal is `non_reserved_seats ?? seats_available`.
- Alerts stop at a per-section cutoff: `public.section_alert_cutoff(start_date, end_date)` (SQL, the only copy of the rule) is ASU's add deadline (start + 6 days for classes over 70 days, else start + 1) plus 14 days' grace, capped at the end date, compared in America/Phoenix by `public.section_alerts_ended`. `get_sections_to_check` skips ended sections, the watch APIs return `alerts_ended` (via `sectionAlertsEnded` in `lib/db/queries.ts`) for the UI, and `POST /api/class-watches` rejects an ended section with 409. Dates come from ASU on each Section Check; unknown dates (NULL) never end alerts. Change the rule with `CREATE OR REPLACE` in a new migration.

**Auth and edge**:
- After consent or admin changes, call `invalidateAuthorizationState`. `proxy.ts` caches `readAuthorizationState` for 30s.
- CSP has two production shapes in `proxy.ts`. Session requests get a per-request nonce. Session-less public pages are edge-cached and get `'unsafe-inline'` with **no** nonce or hash, because either one makes browsers ignore `'unsafe-inline'`. An empty `'nonce-'` once blanked the homepage for anonymous users and Googlebot.
- Never add `headers()` / `cookies()` to `app/layout.tsx`: static pages then 500. `useSearchParams` needs a `<Suspense>` boundary.
- `lib/clerk/config.ts` holds the public Clerk key as a **string literal** on purpose. `process.env.NEXT_PUBLIC_*` does not get inlined into the Worker build.

**Cloudflare config:**
- Workflow `class_name`s in `wrangler.jsonc` must match the classes re-exported from `worker.ts`. Cron schedules live on the Workflow bindings; `triggers.crons` stays `[]`. `CronLockDO` was deleted in migration `v3`, so never reuse that name.
- Workers Free plan limits: Workflow steps get 10ms CPU and 1,024 steps per instance, so keep steps small and I/O-bound. Queues allow roughly 10k ops/day (~3 per message). The DLQ `pickmyclass-dlq` has no consumer; inspect or redrive it from the dashboard.
- Secrets (`CLERK_*`, `ASU_API_*`, `CRON_SECRET`, `UNSUBSCRIBE_SIGNING_SECRET`) are set with `wrangler secret put`, never in `wrangler.jsonc`. Local values go in `.dev.vars` and `.env.local`, both gitignored; `.env.example` lists them.
- `lib/cloudflare-env.d.ts` is **generated** by `pnpm run cf-typegen`, which also rewrites the whole runtime-types section. Commit only the binding hunks unless you mean to bump runtime types. Hand-written additions go in `lib/cloudflare-env.supplemental.d.ts`.
- A new file imported by `worker.ts` must be added to `tsconfig.worker.json` → `include`, or it is never type-checked. `worker.ts` and `scripts/` are also excluded from lint.
- Local `dev` / `preview` reach Postgres at `wrangler.jsonc`'s `localConnectionString` (`localhost:5432`); override with `CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_HYPERDRIVE`.

**SEO**:
- A new indexable page needs an entry in `PUBLIC_PAGES` (`lib/seo/public-pages.ts`) and, for non-blog pages, a date in `lib/seo/static-page-lastmod.json`. The pre-commit hook re-stamps that date via `lib/seo/lastmod-routes.ts`.
- Rendered `<title>` must be ≤60 chars (templates append ` | PickMyClass`; use `{ absolute }` when the title already names the brand). Descriptions must be ≤160 chars.
- `/llms.txt` and `/llms-full.txt` are route handlers. Never add `public/llms*.txt`, because the static file would shadow the route. `public/<key>.txt` must match `INDEXNOW_KEY`.

**Toolchain:**
- Bump `vite-plus`, `vite`, `vitest` and `@vitest/*` together, never one at a time: a solo bump desyncs them and breaks types and coverage. They are declared once in `pnpm-workspace.yaml` — `catalog:` entries plus the `catalog:`-backed overrides — so bumping the carets there moves every consumer; do **not** run `vp migrate`, which rewrites those entries as exact pins. `@vitest/coverage-v8` must keep resolving to the Vitest version `vite-plus` bundles (`vp --version` prints it), or `vp test --coverage` aborts. Dependabot offers them in the `vite-plus-toolchain` group (see `.github/dependabot.yml`) so the set arrives in one PR. There is no direct `oxlint` or `@oxlint/plugins` dependency: `oxlint` comes through `vite-plus`, and the vendored anti-slop plugin imports from `vite-plus/lint/plugins`.
- `tools/oxlint/anti-slop/` is vendored and excluded from lint, fmt, tsc and knip on purpose. `vendor/` is un-ignored in `.gitignore`; keep the whole tree committed (CI lint can't load the plugin otherwise).
- `pnpm-lock.yaml` contains two YAML documents (env lockfile, then project lockfile). That is expected. Changing `packageManager` requires regenerating the lockfile, or CI's `--frozen-lockfile` fails. pnpm 12 errors on unknown `pnpm-workspace.yaml` keys.
- Dependency policy: every version is a caret range (`packageManager` is the sole exact pin). pnpm's default 1440-minute `minimumReleaseAge` applies (non-strict); `pnpm-workspace.yaml` pins exact-version `minimumReleaseAgeExclude` entries for the versions admitted by the 2026-10-22 one-shot security upgrade, so future releases of those packages stay gated and the entries can be deleted once those versions age in. `trustPolicy: no-downgrade` is the permanent supply-chain setting. `pnpm update --latest` keeps `catalog:` references and moves the catalog entries; Dependabot keeps its 1-day cooldown.
- Dependency automation: `.github/dependabot.yml` runs Dependabot daily for npm and GitHub Actions with a 1-day cooldown on version updates (security updates skip cooldown). Minor/patch updates are auto-merged; majors are not — the workflow requests a review from `@Divkix` instead, and the group ordering there is load-bearing (first match wins, so `vite-plus-toolchain` must stay above `all-minor-patch`).
- The auto-merge gate is `.github/workflows/dependabot-automerge.yml` (`pull_request_target`). It is metadata-only: no checkout, no install, no PR code executed, no PR artifact used, and it merges with `gh pr merge --squash --match-head-commit` (the branch is removed by the repo's `delete_branch_on_merge`, not by a flag). A merge needs a Dependabot-authored, same-repo, non-draft PR against `main` — revalidated on every poll and once more immediately before the merge — then `CI Success`, `GitGuardian Security Checks` and `Workers Builds: pickmyclass` present **and** successful, and every other observed check/status an exact `success`: `skipped`, `neutral`, `cancelled` and pending all refuse. It excludes its own check run by suite (this workflow's runs on the head commit), never by name alone, so a same-named check run from any other workflow still gates the merge. Every rollup and status read is paginated. It runs from `main`, so it is inert until this file is merged, and manual edits to it only take effect after merge. `pull_request_target` is allowed for exactly this file and the Dependabot bot by [Actions policy #7005](https://github.com/Divkix/pickmyclass/settings/actions/rules/7005), because GitHub blocks that event on public repos by default from 2026-11-02; a human-authored `synchronize` therefore cannot wake the gate, only Dependabot's own pushes can. `main` also requires branches to be up to date, which the gate does not rebase: a Dependabot PR that falls behind passes its checks and then fails the merge call loudly, so rebase it (or let Dependabot) and the next run merges it.

## Definition of done

1. `pnpm run verify` passes. This is the CI `quality` gate and the pre-commit hook.
2. `pnpm run test:coverage` passes and produces coverage reports (CI `test` job; no minimum threshold).
3. `pnpm run build` passes (CI `check` job).
4. If you touched `worker.ts`, `wrangler.jsonc`, the Workflows or the queue path, run `pnpm run preview` as well.
5. Schema changes ship as committed `migrations_pg/` files (incl. `meta/`) generated from `lib/db/schema/`.
6. Update this file if the change made anything here false.
